# コード対応ゲーム基盤 — 設計と実装状態

更新: 2026-10-28。従来のJSON中心の拡張計画を更新し、**作者のコードでルールとUIを派生開発できること**を中心にする。JSON編集は簡易制作の入口として残す。

## 今回、動くようにしたこと

- `/studio/code` から島の工房のコードキットをZIPで取得。`pnpm kit:export <新しい出力先>` でも同じソースを出力する。
- 出力にはルール・盤面・CPU・独自UI・テスト・SDK・ローカルホストが入る。本体のアカウント・DB・サーバー認証ソースは含めない。
- Node 24で依存インストールなしにテスト・起動。別ブラウザで別席に入り、同じローカルホストで対戦できる。
- 席の秘密トークン、サーバー乱数、合法手、revision、再送の重複排除、非公開情報の投影、固定版別の保存を実装。
- ゲームコードとUIを変更した派生版がホストの変更なしで動くことを統合テストで確認する。
- 外部AI用の依頼書、変更対象ファイル、契約テストを同梱。

これは**ローカル開発の実証版**。クラウドのアップロード実行、GitHub自動フォーク・接続、プレビュー配信、本番公開はまだない。ローカルNodeプロセスはOSユーザーの権限で実行するため、未確認の第三者コードを受け入れる本番環境へ転用しない。

## リポジトリの境界

| 論理リポジトリ | 所有するもの | 現状 |
|---|---|---|
| board-hub | 一覧、作者、認証、部屋、保存、公開管理、実行先への配送 | 現行リポジトリ |
| boardhub-sdk | GameDefinition、CodeGame、状態と操作の契約、接続プロトコル | `engine/` と `sdk/`。キットへ同梱、独立パッケージ化は今後 |
| game-isleworks | ルール、盤面、CPU、UI、素材、テスト、manifest | キットとして切り出せる。GitHub上の別リポジトリは未作成 |
| 派生ゲーム | 元ゲームのフォークと独自変更 | 作者がゲーム用リポジトリを作成後、通常のForkが可能 |

GitHubのフォークはリポジトリ単位。BoardHub本体の一部を毎回抽出するより、ゲームだけを独立させてフォークする。初回キットには動作再現用にSDKとローカルホストも同梱するが、作者の変更範囲は `game.ts`、`games/`、`ui.html`、`tests`、manifestを基本とする。

キットの配布はフォルダのコピーでありGitHubのフォーク履歴はまだない。`forkOf` は作者が記録するメタデータで、現段階ではサーバー検証された派生証明ではない。

## 作者が実装できる契約

`CodeGame` はゲームの開始処理、クライアント操作のパーサー、乱数確定、GameDefinition、任意のおすすめ操作を接続する。

- `setup / validate / reduce / playerView`: 状態・合法手・遷移・非公開情報。
- `startAction`: 人数に応じた初期化操作をサーバーで生成。
- `parseAction`: クライアントが送れる操作だけを受け入れる。
- `resolveAction`: ダイス・抽選・非公開の山札からの取得をサーバーで確定。
- `ui.html`: 完全なゲーム固有画面。開発用の最小UIなので元の本格UIとは異なる。

v0.1は2〜4席の直列の手番進行。独自フェーズ・新アクション・地形・建物等はゲームコードで実装できる。任意人数や同時操作を実現済みとは扱わず、必要に応じてSDKを拡張する。

## GitHub接続の設計（次段階）

1. 作者がGitHubでゲーム用リポジトリを作る/フォークする。
2. BoardHub GitHub Appを選択したリポジトリだけに導入。installation ID、repo ID、作者、ゲームIDの対応を保存。
3. 初期権限はメタデータ・ソース読み取りと検証結果の書き込みを基本とする。ZIPから変更ブランチを作る段階でContents書き込み、PRを作る段階でPR書き込みを追加。GitHub Appが新規リポジトリを作成できるとは前提にせず、初回は作者が作成する。
4. Webhookは署名・delivery ID重複・インストール状態・対象repo・ブランチ/コミットを検証。キューに固定commit SHAのビルド要求を保存。
5. デフォルトブランチへのpushでも自動公開しない。ビルド成功は「試遊可能」を意味する。
6. BoardHub上で作者が試遊済み成果物を選んだときに公開先を切り替える。

GitHubリポジトリへの接続は、第三者作品を勝手に配信してよいという意味にしない。作品所有者・派生許可・ライセンスとGitHub連携権限を別に検証する。

## ZIP取り込みの設計（次段階）

ZIPアップロード→サイズ/件数/展開量/パス/シンボリックリンク検証→manifest検証→作者の変更ブランチにコミット→GitHub接続と同じビルドキューへ。

`.github/workflows`、秘密鍵、環境変数、任意の配信設定をそのまま実行しない。ビルドはプラットフォーム管理の手順で行う。拡張子の許可だけを安全な実行の根拠にしない。追加依存の許可ポリシーも必要。

## ビルド・実行の分離（本番の前提）

- ビルド: 外部コードと依存インストールを隔離した短命な環境で実行。GitHub書込権限・Cloudflare配信権限・本番DBを渡さない。CPU/メモリ/時間/出力量/ネットワークを制限。
- 検証: SDK互換、公開API、合法手、非公開情報、テスト結果、成果物を確認。テストが通ること自体は隔離の代わりにならない。
- 配信: 信頼された処理だけが検証済み成果物を読み、隔離実行先へ登録。配信鍵をゲームコードに渡さない。
- サーバールール: Workers for Platforms等の隔離環境へ、作品/固定版ごとに配置。本体が席・revision・操作IDを検証してから実行を呼ぶ。ゲーム実行はDBを持たず、限定された状態と操作を受け取り遷移結果を返す。出力サイズ・形式・次席も本体が検証し、CASで保存。乱数再試行は固定したサーバー生成コンテキストを使う。
- UI: 本体とは別オリジンの静的アセットをsandbox iframeで表示。UIに本体Cookieや部屋の席トークンを渡さない。親が認証を保持し、フレームごとのMessageChannelで許可したゲーム操作と投影済み状態だけを交換。送信元、接続nonce、プロトコル、作品/版/部屋を検証する。
- 秘密情報を隠す最終責任はゲームの `playerView` にもある。自動検査と公開前確認を行い、任意コードから情報漏洩が絶対起きないとは保証しない。

## 固定版・保存・公開モデル

| レコード | 主な情報 |
|---|---|
| code_projects | 所有者、repo ID、派生元、ライセンス、公開ポインタ |
| code_builds | source SHA/ZIP digest、SDK版、依存lock digest、status、エラー |
| code_releases | ソース・UI・ルール・SDKを含む成果物digest、隔離実行先、準備状態 |
| code_rooms | project ID、release ID、状態、revision、参加権限 |
| code_feedback | project ID、release ID、room ID（任意）、投稿者、本文 |

状態は queued→building→failed/ready。readyな成果物だけ試遊可能。公開は別ポインタで管理し、作者認証・期待する現公開版の一致を確認して更新する。検証した成果物をそのまま昇格し、公開時に別ビルドしない。

進行中の部屋はrelease IDを固定。公開先を戻しても既存部屋は開始時の版で続く。削除/無効化する版の利用中部屋を調べ、保持期間と非常時停止を設計する。

ローカル実証版は固定版ごとの保存先を分けるだけで、単一ホスト上で複数版を並行配信するものではない。旧版は別ディレクトリ・別ポートで起動する。

## 実装順・受入条件

1. **今回: 独立コードキットとローカル試遊**。ゲームコードだけの新アクション・UI変更をホスト変更なしで実行、2席認証・秘密情報・再送・保存・版分離を検証。
2. **隔離実行の技術検証**。無限ループ、巨大出力、外部通信、他作品/本体DBへのアクセスを制限し、失敗しても他の部屋が動くことを確認。Cloudflareアカウントの機能・費用を確認して採用。
3. **GitHub Appとビルドキュー**。正しいrepoの固定commitだけがビルドされ、重複Webhookが二重配信しない。
4. **固定版試遊URLと本体ルーム接続**。インターネット越しの2〜4人試遊を実証。
5. **ZIP取り込みと公開操作**。同じビルド経路・権限・履歴を使い、作者の操作で公開・復旧。
6. **版に紐づく感想と改善**。外部作者が制作→第三者試遊→改訂まで完了。島の工房から船・海・探検を追加する実例へ進む。

実際の自動配信にはGitHub Appと隔離環境の設定が必要。接続されていないサービスを完成済みとして表示しない。
